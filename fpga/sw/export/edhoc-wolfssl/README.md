# EDHOC on RV64 — Methods 0–3, all RFC 9528 suites

Bare-metal [EDHOC](https://datatracker.ietf.org/doc/rfc9528/) (RFC 9528) firmware
for the 64-bit Rocket core of `EdhocRocket6475MHzArty100TConfig` (Arty A7-100T,
75 MHz, 64 KiB scratchpad). All four authentication methods and every standard
cipher suite, pure software (`rv64imac`, `lp64`).

## What's inside

| Method | Initiator auth | Responder auth |
|:------:|----------------|----------------|
| **0** | Signature | Signature |
| **1** | Signature | Static DH |
| **2** | Static DH | Signature |
| **3** | Static DH | Static DH |

| Suite | Primitives |
|:-----:|-----------|
| 0 | AES-CCM-16-64-128 · SHA-256 · X25519 · EdDSA |
| 1 | AES-CCM-16-128-128 · SHA-256 · X25519 · EdDSA |
| 2 | AES-CCM-16-64-128 · SHA-256 · P-256 · ES256 (default) |
| 3 | AES-CCM-16-128-128 · SHA-256 · P-256 · ES256 |
| 4 | ChaCha20/Poly1305 · SHA-256 · X25519 · EdDSA |
| 5 | ChaCha20/Poly1305 · SHA-256 · P-256 · ES256 |
| 6 | AES-128-GCM · SHA-256 · X25519 · ES256 |
| 24 | AES-256-GCM · SHA-384 · P-384 · ES384 |
| 25 | ChaCha20/Poly1305 · SHAKE256 · X448 · Ed448 |

Where each primitive comes from:

| Primitive | Implementation |
|-----------|----------------|
| SHA-256/384, HMAC/HKDF, AES-CCM/GCM | `../common/crypto` (shared with edhoc-authkem) |
| ChaCha20/Poly1305, Ed25519 | Monocypher (`../common/externals/monocypher`) |
| X25519 | curve25519-donna-c64 (`../common/externals/curve25519-donna`) |
| P-256/P-384 (ECDH, ECDSA), X448, Ed448, SHAKE256 | wolfCrypt v5.9.1 (`wolfssl/`) |

`wolfssl/` holds only the wolfCrypt sources and headers these suites compile,
plus `user_settings.h`.

## Prerequisites

A bare-metal RISC-V GCC with an `rv64imac`/`lp64` multilib, e.g.
[riscv-gnu-toolchain](https://github.com/riscv-collab/riscv-gnu-toolchain),
providing `riscv64-unknown-elf-gcc`. Put it on `PATH` or pass the prefix:

```bash
make edhoc_m3_initiator CROSS_COMPILE=/opt/riscv/bin/riscv64-unknown-elf-
```

The package needs its sibling `../common/` (platform, radio, CBOR, EDHOC core,
symmetric crypto, linker script, board scripts). Ship `export/` as a whole.

## Build

```
make <target> CRYPTO_SUITE=<n> [TRANSPORT=rf|uart] [DEBUG=1] [TIMING=1]
```

Targets, one per method × role:

```
edhoc_m0_initiator   edhoc_m0_responder
edhoc_m1_initiator   edhoc_m1_responder
edhoc_m2_initiator   edhoc_m2_responder
edhoc_m3_initiator   edhoc_m3_responder
```

```bash
make edhoc_m3_initiator CRYPTO_SUITE=2      # Static-DH/Static-DH, P-256
make edhoc_m0_responder CRYPTO_SUITE=25     # Signature/Signature, X448 + Ed448
```

Targets share `build/`; objects are rebuilt automatically whenever the flags
change (suite, method, role, transport, profile), so no `make clean` is needed
between targets. Output: `build/<target>.elf` (+ `.bin`, `.map`).

Options:

* `TRANSPORT=rf` (default): messages travel over an MRF24J40 802.15.4 module on
  PMOD JC (SPI1 @ `0x64006000`); the bitstream must include `WithArtyJCRadio`.
  `TRANSPORT=uart` uses three wires between the two PMOD JB ports instead (TX and
  RX crossed, GND), 921,600 baud (`UART1_BAUD=` to change) with receiver-driven
  flow control: about 3× the radio's speed for files.
* `DEBUG=1` step-by-step prints (incl. `PRK_out`).
* `TIMING=1` prints, after the handshake, the compute time of each message
  step (`msg1_build`, `msg2_process`, `msg3_build` on the initiator,
  `msg2_build`, `msg3_process` on the responder) as `PERF` lines.
  `../common/board/perf_table.py <logdir>` turns a set of board logs into one
  table. Encrypt/decrypt time and throughput of the application channel are
  always printed (`PERF encrypt` / `PERF decrypt`).
* `APP_FILE_BYTES=<n>` streams n generated bytes through the encrypted channel
  after the handshake.
* `EXTRA_CFLAGS=-DAPP_SD_XFER` sends a real file card to card: the initiator
  reads `SEND.BIN` from the FAT32 partition of its SD card (PMOD JA), the
  responder writes it as `RECV.BIN` on its own card, committed only when the
  length and CRC-32 match. Prepare each card once with `../tools/mksd.sh`,
  then copy `SEND.BIN` on with any PC. Without a card reader, `../tests`
  `make sd_prep` formats the card and writes a test `SEND.BIN` over JTAG.
  Any size up to 4 GiB; RAM use is flat; about 10 KB/s over the radio.
* `PROFILE=production PROVISION_SRC=<files>` refuses demo keys and the
  cycle-counter RNG; see `include/edhoc_provision.h`.

Host check without hardware: `make loopback-test CRYPTO_SUITE=<s> METHOD=<m>`
runs initiator and responder as two threads and compares `PRK_out`.

RFC 9529 test vectors: `make rfc9529-test` runs each role against the two
"Traces of EDHOC" (Trace 1: Method 0, suite 0, x5t; Trace 2: Method 3,
suite 2, kid, with cipher-suite negotiation). Every message sent, `PRK_out`,
`PRK_exporter` and the OSCORE master secret/salt must equal the RFC byte for
byte, and each of the 15 invalid messages of RFC 9529 Section 4, plus a
message_1 with an unrecognized critical EAD item (RFC 9528 3.8), must be
rejected with the expected error (4.2.1, a P-384 case, runs in a suite 24
build). It also checks that the received ID_CRED reaches the application and
that refusing it stops the handshake. `make rfc9529-images` builds the same
test for the board (`build/rfc9529_s{0,2,24}.elf`; load with
`../common/board/run_one.sh`). Vectors: `tests/rfc9529_vectors.h`.

Peer credentials: the library looks the received ID_CRED up in the trust
anchors (`cred_array`). To see it first, as RFC 9528 3.5 requires the
library to allow, set `id_cred_check` (and `params_id_cred_check`) in the
initiator or responder context: it is called with ID_CRED_R / ID_CRED_I in
map form before the credential is used, and any return other than `ok`
aborts the session with an error message. Leaving it NULL accepts every
ID_CRED found in the trust anchors.

## Running on two boards

Load over the C232HM JTAG cables on PMOD JD (responder first) and watch the two
USB-UART consoles at 57600 baud:

```bash
../common/board/load_both.sh build/edhoc_m3_initiator.elf build/edhoc_m3_responder.elf
```

Cable and console serials live in `../common/board/boards.env`; `../common/board/list_boards.sh`
prints yours. `../common/board/run_one.sh`
loads one board and prints its console; `../common/board/sd_boot.sh` writes a
`.bin` to the SD boot partition instead.

Each side prints `EDHOC OK!`, `PERF` lines (cycles and seconds for the total,
link and compute parts of the handshake), its peak stack, then runs the
application-data echo below and prints `APP DATA OK`.

`../common/board/run_pair.sh <name> <initiator.elf> <responder.elf>` loads both,
judges both consoles and prints one line, e.g.
`s2_m3 PASS hs=2.740934s stack_i=5360 stack_r=4736 prk=- 7s` (`prk=match` when both
consoles print `PRK_out`, as with `DEBUG=1`). `VERBOSE=1 ../common/board/run_pair.sh ...`
also shows both consoles live (`I|` / `R|`); build with `DEBUG=1` to see every
intermediate value (TH_2, PRK_2e, K_3, MAC_2, ...).

## Application data after the handshake

`../common/src/edhoc_app_data.c` is suite-independent:

* keys come from the RFC 9528 §4.2.1 exporter,
  `PRK_out -> PRK_exporter -> (K_app, IV_app)`, with the suite's hash;
* the AEAD is the suite's application AEAD, with key, IV and tag lengths read at
  run time, so AES-CCM, AES-GCM-128/256 and ChaCha20/Poly1305 share one path;
* each record is `ciphertext || tag`. The nonce is `IV_app XOR (dir || seq)`,
  `dir` 0 for initiator→responder and 1 for the reverse, so the directions never
  share a nonce; the same 5-byte header is the AAD and is not transmitted.

To send your own data, call `app_data_init()` once, then `app_data_send()` /
`app_data_recv()` (see `../common/include/edhoc_app_data.h`).

## Layout

```
Makefile            includes mk/config.mk, ../common/mk/rules.mk, mk/targets.mk
mk/config.mk        cipher-suite table, profile, stack per suite, includes
mk/targets.mk       the eight method x role targets, no-LTO wolfCrypt objects
src/                initiator/responder mains, EDHOC app glue, board reporting
include/            app headers, demo keys, provisioning interface
tests/              host loopback test
uoscore-uedhoc/     EDHOC Methods 0-3 library (RFC 9528)
wolfssl/            wolfCrypt subset + user_settings.h
../common/          platform, radio, CBOR, EDHOC core, crypto, linker, board scripts
```
